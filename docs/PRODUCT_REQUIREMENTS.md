# Product requirements — AI SRE Incident Investigation Platform

## Product goal

Create a reproducible local platform that detects failures in a demo microservice system, automatically gathers real telemetry, performs evidence-first AI investigation, proposes a root cause and safe remediation, and waits for human approval before executing any change.

The project is a portfolio application for a Software/AI Engineer role. It must demonstrate backend engineering, observability, agentic workflows, RAG, evaluation, security, DevOps, and cloud delivery without hiding weaknesses behind a polished UI.

## Primary user

An SRE or software engineer investigating a production-like incident who needs:

- a normalized incident and timeline;
- correlated metrics, logs, traces, and deployments;
- multiple competing hypotheses;
- evidence-backed verification or rejection;
- an honest insufficient-evidence result;
- a remediation recommendation with risk;
- explicit human approval and an audit trail.

## Functional scope

### Demo application

The demo system contains:

- `gateway`;
- `order-service`;
- `inventory-service`;
- `payment-service`;
- PostgreSQL.

`POST /checkout` traverses gateway → order → inventory → payment → PostgreSQL and returns an order result. Each hop propagates distributed tracing context.

### Observability

Every service provides:

- request count, latency histogram, and error metrics;
- structured logs correlated with trace and span IDs;
- distributed spans with service/version/environment attributes;
- health and readiness endpoints.

Local infrastructure includes OpenTelemetry Collector, Prometheus, Alertmanager, Loki, Tempo, and Grafana.

### Incident lifecycle

Alertmanager sends a webhook to the Incident API. Ingestion:

1. validates and normalizes the alert;
2. applies idempotency/deduplication;
3. creates or updates an incident;
4. enqueues investigation work;
5. returns HTTP 202 quickly.

Supported status progression:

`queued → investigating → waiting_for_approval → remediating → verifying → resolved`

Failure/alternative states include `insufficient_evidence`, `investigation_failed`, `rejected`, and `closed`.

### Evidence collection

Deterministic adapters collect bounded, timestamped evidence from:

- Prometheus: latency, error rate, CPU, memory, DB pool;
- Loki: errors, patterns, logs around a timestamp;
- Tempo: slow traces, a trace, service dependencies;
- deployment storage: version, commit, changed files, deployment time;
- knowledge storage: runbooks, architecture documents, prior incidents.

### AI investigation

The workflow:

1. normalizes scope and investigation window;
2. plans required evidence;
3. collects independent evidence in parallel where safe;
4. correlates a timeline;
5. retrieves relevant historical knowledge;
6. generates multiple hypotheses;
7. verifies and rejects hypotheses using evidence;
8. loops for additional bounded collection when necessary;
9. emits a schema-valid `IncidentReport`;
10. proposes but does not execute remediation.

Every claim in a hypothesis or root cause must cite evidence IDs. Correlation alone cannot be presented as causation. When support is inadequate, root cause is null.

### Human approval

The UI lets a human approve or reject a recommendation. Approval records actor, timestamp, recommendation, and current incident/version state. In the local demo, an approved rollback calls an allowlisted demo control endpoint. The LLM never receives arbitrary execution capability.

### Controlled fault scenarios

At minimum:

- slow database;
- database pool exhaustion;
- high error rate;
- bad payment deployment;
- upstream inventory timeout;
- CPU saturation;
- healthy/no real incident.

Faults are disabled by default, explicit, reversible, visible in the UI/logs, and isolated to the local demo.

### Evaluation

The evaluation runner executes deterministic scenarios and calculates root-cause accuracy, top-3 accuracy, false-root-cause rate, evidence precision/recall, unsupported-claim rate, latency, cost, and tool calls.

## Non-functional requirements

- Local happy path starts with one documented command.
- A clean-machine setup is reproducible from committed files and lockfiles.
- All external calls have timeouts and bounded retries.
- Investigation execution is idempotent and restart-safe.
- Timestamps are UTC and time windows are explicit.
- Secrets remain outside source control and model context.
- Critical flows are testable without live LLM calls.
- The system exposes telemetry about the investigator itself.
- The final 3–5 minute demo can be repeated reliably.

## Out of scope for MVP

- Autonomous production remediation;
- arbitrary shell, SQL, PromQL, LogQL, or `kubectl` generated by the LLM;
- multi-cloud production support;
- a full observability product or log explorer;
- sophisticated authentication/SSO;
- mobile application;
- model fine-tuning;
- starting with RAG before telemetry and incident ingestion work.

## Final demo acceptance

1. Normal checkout is visible in metrics, logs, and an end-to-end trace.
2. A bad deployment is registered and a controlled regression is enabled.
3. Prometheus fires an alert and Alertmanager creates an incident.
4. The worker collects evidence from at least metrics, logs, traces, and deployments.
5. The investigator produces at least three hypotheses and explicitly rejects contradicted ones.
6. The final report cites evidence and identifies the correct root cause or honestly reports insufficient evidence.
7. A rollback recommendation waits for human approval.
8. Approval executes only the allowlisted local rollback.
9. Recovery is verified from telemetry and the incident becomes resolved.
10. The entire sequence is covered by an automated E2E test.
